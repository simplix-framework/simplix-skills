# simplix-react frontend

simplix-react derives a typed client, query hooks, form hooks and mock handlers from one contract per domain. The contract is written once, usually generated from the API document of the backend, and everything else follows from it.

Verified against 0.3.12.

## Before anything else

Read the version of `@simplix-react/ui` or `@simplix-react/contract` the project resolves, from its package manifest or its workspace catalog. A project on an older version may lack a command, an option or an export named here: `simplix --help` and the type declarations of the installed packages are what that project has, and they win over this handbook.

## Rules

1. Derive, do not hand-roll. Fetching, caching, a form or a mock for something the contract describes comes from `deriveEntityHooks`, `deriveEntityFormHooks` and `deriveMockHandlers`. Do not write a bespoke fetch, query or form state for it.
2. Generate, do not hand-create. A project, a domain package, a feature module and the CRUD screens of an entity are created with the `simplix` command line tool. Where an API document exists, generation from it is the source of truth.
3. Never edit generated files. Change what was generated by wrapping the contract with `customizeApi`, or by changing the API document and generating again.
4. Contracts, schemas, hooks and mocks live in domain packages under `packages/`. Screens live in feature modules under `modules/`. Code derived from a contract is never copied into an app.
5. Inside a module, `features/` does not import from `widgets/`, and `shared/` imports from neither. `simplix validate` checks this, and it has to pass before the work is called done.
6. An entity of a contract is a `schema` and an `operations` map. Each operation carries its own method and path, and the operations that send a body carry their input schema.
7. Extend through the seams the framework gives: a fetch function passed to the contract, `createFetch`, `customizeApi`. Do not rewrite what was derived.
8. A screen is not done because it compiles. Drive it in a browser under the sibling handbook `frontend-e2e` before calling a screen complete.

## Commands

| Goal | Command |
| --- | --- |
| Start a project | `simplix init <name>` |
| Add a domain from an API document | `simplix openapi <spec>` |
| Add a domain by hand | `simplix add-domain <name>`, then write its contract |
| Add a feature module | `simplix add-module <name>` |
| Generate the CRUD screens of an entity | `simplix scaffold <entity> --module <module>` |
| Add an app | `simplix add-app <name>` |
| Set up the UI package | `simplix init-ui` |
| Generate types from translation files | `simplix i18n-codegen` |
| Check structure, layers, imports and translations | `simplix validate` |
| Generate domain packages from SimpliX Meta, and compare the two ways of generating a domain | `simplix meta`, `simplix meta-diff <domain>` |

## Verify

- `simplix validate` ends without an error.
- The type check, the lint and the tests of the workspace pass, run with the scripts the project defines.
- After a change to the API document, the domain was generated again and the diff of the generated folder was read.
- Each screen that changed was opened and driven in a browser: list, filter, sort, open, create, edit, delete, and the empty and failing states.

## Reading the framework documents

A name written as `simplix-react:<path>` is a file of the simplix-react repository at the version the project uses.

- With the sibling handbook installed, `node ../simplix/scripts/framework-doc.mjs simplix-react:docs/en/guides/cli-usage.md --version <version>` prints the page for that version.
- Without it, read `https://raw.githubusercontent.com/simplix-framework/simplix-react/v<version>/<path>`.
- Where a page and the installed types disagree, the types win. `references/contract-and-hooks.md` names the pages of this version that still show an earlier shape of the contract.
